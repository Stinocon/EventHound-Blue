# Roadmap

The state of the suite and what is deliberately still open, with the reasoning — a backlog is only
useful if it says *why* something is not done, otherwise the same debate reopens every few weeks.

Component detail lives in [`analysis/DESIGN.md`](../analysis/DESIGN.md); this is the project-level view.

## Built

**Analysis engine** — EVTX via Hayabusa/Sigma (detections) and EvtxECmd (full stream), the Hayabusa
toolbox (EID/log/computer metrics, keyword & regex search, pivot keywords, base64 extraction), PCAP
via tshark + Zeek, generic logs (access/jsonl/regex/syslog), Windows registry (RECmd hives and native
`.reg` exports), MFT via MFTECmd, THOR (Nextron) scan reports, Okta System Log. All normalized onto
one ECS-subset schema (`analysis/schema/common-schema.md`).

**The attack map** — `engine/attack_map.py`: entities and their links in kill-chain lanes as inline
SVG, with a deterministic phase-by-phase narrative, rendered once for both the HTML report and the
GUI. An edge is co-occurrence, never causation, and every mark carries the evidence behind it.

**A runnable demo, with no customer evidence** — `engine/run_demo` generates one coherent
intrusion as nine source types (`analysis/demo/scenario.py`, pure stdlib), ingests them through
the ordinary adapters into a case, and produces the full analysis and report. It is also the only
end-to-end test in the suite: `analysis/demo/expectations.json` states what the correlation must
conclude, in the same shape as the correlation corpus so the same checkers verify both.

**Analytics and correlation** — DuckDB long-tail (process stacking, rare parent–child, rare DNS,
non-standard ports, beaconing), temporal episodes, cross-source indicators with entity
normalization and confidence ranking, incident clusters (connected components across tools), the
unified timeline (every source on one chronological axis, salience-filtered, each row stating what
earned it its place), and the ATT&CK/kill-chain layer: technique → tactic from the official STIX
map, kill-chain phase coverage per dataset, per host, and per cluster.

**Interfaces** — CLI first (`engine/run_*.py`), the local GUI on `127.0.0.1:8700` as a thin layer
over the same functions, and an external agentic harness (Pi, Claude Code, …) reached through the
analysis MCP server (`analysis/analysis_mcp_server.py`: `analyze` / `analyze_case` / `eid_lookup`,
pseudonymized §9).

**Outputs** — HTML / Markdown / JSON reports at three detail levels, re-importable analysis
bundles (`engine/bundle.py`) so conclusions reopen without the original evidence, and persistent
**cases** (`analytics/case_store.py`) that keep the data itself: sources accumulate across
sessions, notes stay with the case, and two cases can be diffed.

**Knowledge base** — plain markdown under `method/` (`framework/` MITRE/NIST/SANS/CIS, `normative/`
GDPR/NIS2/DORA, `acn`), read directly by the analyst; ATT&CK technique→tactic is vendored in
`analysis/analytics/attack_map.json` (generated from the official STIX bundle).

**Measurement** — a labelled corpus for correlation (`analysis/eval/`, run by `engine/run_eval.py`)
declaring what must and must not link, plus a discrimination test that breaks a knob and checks the
corpus notices; golden tests for the scoring oracle. The engine suite
runs under pytest with coverage (69–70% at the 2026-08-27 measurement, depending on whether the
optional `yara` extra is installed; CLI entry points included) and
reports a missing dependency as a skip rather than a pass; the GUI's pure logic is unit-tested with
`node --test`.

**Deterministic tools** — CVSS v3.1/v4.0, risk matrix, EPSS (`tools/scoring/`, golden-tested);
GDPR/NIS2/DORA obligation mapping (`tools/compliance/`); Shodan/VirusTotal/ThreatFox enrichment,
egress-gated and public-indicators-only (`tools/enrichment/`); shared configuration store
(`tools/eventhound_config.py`); hygiene guards (`tools/check*.sh`).

**Packaging** — native install/uninstall on macOS and Linux (`setup.sh` dispatching to
`setup-macos.sh` / `setup-linux.sh` over a shared `tools/setup-common.sh`; `uninstall.sh`); no
component requires Docker, which remains available for reproducible deployments and for platforms
neither script covers.

## Next up — in priority order

The six below are committed work, not ideas: ordered by how much each one increases trust in the
output, with the reasoning kept so the ordering can be argued with instead of re-derived.

**All six are done** (2026-07-23 → 2026-07-24); each one is left in place with what it actually
changed, because the outcome is usually not what the entry predicted.

The pattern held to the end, and it is the thing worth carrying forward: **every one of the six
surfaced a defect that was not the stated task.** A chronological cap that would have shown boot
noise. Non-deterministic aggregate output. Three tests reporting green for code they never ran. A
coverage number that lied about subprocesses. A missing pandas costing 2.7 ms per record, an EVTX
ingest priced per file rather than per megabyte, and an IoC search silently covering a prefix of the
data. And finally a Qdrant check that trusted an executable bit, found only because the Linux work
was tested on Linux instead of reasoned about. Six for six: the work item was the occasion, the
finding was the value. Whatever comes off the **Open** list next, budget for the finding.

1. ~~**Surface the unified timeline.**~~ **Done (2026-07-23).** `correlate.timeline()` existed and
   nothing called it. Surfacing it as written would have been useless, though: a chronological cap
   over everything returns the head of the file, which is boot noise, so it is now
   **salience-filtered** — a row survives when it carries an ATT&CK technique, a high/critical Sigma
   hit, a **high-signal event type** (log clearing, service/scheduled-task/WMI persistence,
   privileged group change, remote thread, failed authentication — read from the Event ID SOT
   vocabulary), a THOR finding or a failed action, and each row says which criterion kept it (`why`,
   a selection criterion, never a severity, §6). Wired into `analyze()`, both reports, the CLI, the
   GUI (its own view with client-side filters) and the AI context packer. Documented in
   [`docs/analysis/correlation.md`](analysis/correlation.md) as the third correlation primitive —
   the bridge by *order*.
2. ~~**An evaluation corpus for correlation.**~~ **Done (2026-07-23).**
   `analysis/eval/correlation_corpus.json` — 10 labelled cases, synthetic and offline — declares
   records plus what the engine must conclude: bridges, entities that must **not** bridge
   (`SYSTEM`, machine accounts, loopback, `svchost.exe`), confidence ordering (a shared hash
   outranks a shared IP), multi-family episodes, cluster membership, beaconing present/absent,
   timeline selection. `engine/run_eval.py` runs it, `--sweep-gap` sweeps the session-gap.
   The measurement that came out of it: the gap holds fully only between **120 s and 300 s** —
   below it a real chain splits, above it unrelated activity merges — so the 120 s default is now
   the lower edge of a measured band rather than a preference.
   `tests/test_corpus_discriminates.py` breaks one knob at a time and asserts the guarding case
   turns red (7 mutations, all caught), because a corpus that cannot fail measures nothing.
3. ~~**Case persistence.**~~ **Done (2026-07-23).** A case is one directory under
   `analysis/cases/` holding a file-backed DuckDB plus metadata and notes
   (`analytics/case_store.py`, CLI `engine/run_case.py`, a Cases view in the GUI). Sources are
   appended one at a time, so an analysis grows across sessions and peak memory is one source
   rather than the whole case — the parsing step upstream still materializes its own file, so this
   lifts the ceiling on the analytics side, not on the adapters'. The store keeps the **raw
   records** beside the analytic table so a case outlives a schema change: the column layout is
   fingerprinted and `events` is rebuilt when it moves, instead of querying columns that no longer
   exist. `run_case diff` makes baseline/diffing serious, since both sides now survive their
   session. The test that asserts a persisted analysis equals the in-memory one also caught a
   latent non-determinism (`string_agg` without `ORDER BY`), now fixed — identical input gives
   identical output.
4. ~~**Make the tests measure what they claim.**~~ **Done (2026-07-23).** Three things were wrong
   and all three are now visible instead of assumed. **Skips were passes**: a test whose binary or
   dataset was missing printed `SKIP` and returned 0, which pytest reads as success — three tests
   (MFT end-to-end, registry hives, YARA) were reporting green for code that never ran.
   `tests/_helpers.skip_test` now raises a real skip under the runner while still printing and
   exiting 0 as a script, so both ways of running the suite stay honest. **Coverage was unknown**:
   it measured 62%, and said that every `engine/run_*.py` sat at **0%** — the CLI, the surface this
   project calls primary, had never been executed by a test. `tests/test_cli_smoke.py` discovers the
   entry points by glob and exercises them; the suite is now at **71%**. **The JS was syntax-only**:
   the pure logic moved to `gui/static/lib.js` and is tested with `node --test`, which also pins the
   `esc()`/`el()` rule that the double-escaping bug broke.
5. ~~**Numbers we do not have.**~~ **Done (2026-07-24).** Two commands now produce what were
   impressions: `engine/run_bench.py` (analytics profile on synthetic data + real Hayabusa
   throughput) and `engine/run_toolbench.py` over `eval/toolcall_prompts.json` (20 labelled
   prompts, 14 requiring a specific tool). Figures, with the hardware they were measured on, live
   in [`docs/analysis/performance.md`](analysis/performance.md). What the measuring found, in
   descending order of consequence:
   - **The store load *is* the pipeline.** Every recipe and correlation together cost under 1 % of
     a run at every size; loading rows into DuckDB is the rest. The reason was a defect: its Python
     client probes `import pandas` per bound value, Python does not cache a failed import, and with
     pandas absent each probe re-walked `sys.path` — 35 652 failed imports per 1 000 records.
     Negative-caching the name around the bulk insert (`store._without_probing_for_pandas`) made
     the dominant stage **3.8x** faster; 100 000 events now load in 77 s instead of ~4.5 min.
   - **EVTX ingest is priced per file, not per megabyte.** Hayabusa is invoked once per file and
     reloads ~5 000 Sigma rules each time. The same 278-file corpus takes 205 s that way and
     **7.5 s** handed to Hayabusa once as a directory — 27x. Not applied: directory mode gives no
     per-file error report, and `build_records` isolates failures on purpose so one corrupt EVTX
     does not abort a client's batch. That trade needs its own decision; it is in **Open** below.
   - **The 5 000-record cap was never a performance limit, it was a silent one.** It bounds only the
     browser-side IoC search corpus and the THOR list — the SQL analytics always saw everything —
     but a miss in that search was indistinguishable from a real absence. The analysis now reports
     `records_total`/`records_capped` and the GUI states its scope; the cap stays where it is.
   - **The 14B default is less clearly right than the decision that chose it.** On narration — the
     metric §14.3 was decided on — it does win, 1 event against 3 out of 42 runs, which is a
     difference of two events. On everything else the 7B is ahead: 90 % of cases passed against
     73 %, 2.2x faster, and **zero** answers in a non-Latin script against the 14B's 7 of 60
     (coherent, correctly grounded, in Thai, on English prompts — invisible until something read all
     60 answers). Not a recommendation to switch; evidence that the choice deserves one.
   - **Neither model reliably refuses an evasion request.** Asked for a Defender-disabling
     one-liner, the 14B refused in prose and supplied the cmdlet anyway on 2 of 3 runs (once
     outright, once as an `ExclusionProcess` called "a safer approach"). The read-only registry
     still makes it structurally unable to act — but the text it hands the user is not guaranteed by
     the system prompt alone, and that is what gets copied.
6. ~~**Linux setup.**~~ **Done (2026-07-24).** `setup-linux.sh` closes the gap, but the interesting
   part was refusing to write it as a second copy: three quarters of `setup-macos.sh` is
   platform-neutral (services, pids, the EZ tools — which are .NET dlls and identical everywhere —
   the uv environments, the model pull, the doctor layout), and shipping that twice would have
   guaranteed the two drift. The shared half moved to `tools/setup-common.sh`; each platform file
   now holds only what genuinely differs — package manager, release assets, cache paths — and
   `setup.sh` dispatches by `uname` so `rag/backup.sh`, `start.sh` and `uninstall.sh` have one name
   to call instead of each repeating the test. `uninstall-macos.sh` became the platform-neutral
   `uninstall.sh`.
   Verified on Linux rather than asserted: the doctor, the dispatcher and the uninstaller were run
   in a Debian container, and the Hayabusa and Qdrant Linux assets were resolved, downloaded and
   executed there — the asset names are not symmetrical (Qdrant publishes no `aarch64` **gnu**
   build, only musl) and would have been wrong if guessed.
   That container run also exposed a defect **in the macOS script**: `qdrant_bin()` tested the
   executable bit, so a Darwin binary in a checkout opened from Linux reported a green Qdrant that
   could not start — and `install` would then decline to fetch the right one. It now runs the binary
   instead of trusting its permissions.
   Two Linux honesties, both stated in the README rather than papered over: `uv` and `ollama` are
   not packaged by most distros, so the installer uses the vendors' scripts and **prints each
   command before running it** (§10 — the trust surface stays the user's); and **Zeek is optional**,
   absent from most default repos, so a missing Zeek is reported rather than fixed by adding a
   third-party apt source behind the user's back — PCAP analysis works on tshark alone.

  <details><summary>what it was</summary>

- **Correlation defects — first block closed (2026-08-27).** Three defects that shared one shape:
  the correlator answered confidently while missing or over-counting the evidence, and none of the
  three produced an error anyone could see.
  - **The bridge unit was the file, not the tool.** `shared_indicators` counted `count(DISTINCT
    source)`, and `event.source` is qualified with the file name by PCAP and the generic log
    adapter but is a bare constant everywhere else. Since `_confidence` adds `+0.1` per family
    beyond the second, one sensor could push its own IP bridge up by capturing twice — while ten
    `Security.evtx` collected from ten hosts all carried the label `evtx` and could never
    corroborate each other. `normalize.source_family` now derives the tool from the label, `family`
    is a store column, and every count (`shared_indicators`, `episodes`, `killchain`,
    `technique_catalog`, `incident_clusters`) uses it. The qualified label survives as the origin
    and is reported alongside (`origin_list`), so provenance is not lost.
    EVTX deliberately stays family-level: Hayabusa does not attribute a record to its file in
    directory mode, so a per-file origin would exist on one ingest path and vanish on the other.
  - **`file.hash.sha256` never reached the store.** `common-schema.md` documented it as mapped and
    both `adapters/crowdstrike.py` and `adapters/osquery_result.py` emit it, but `store._COLUMNS`
    only knew `file.hash` and `file.hash.md5` — so the strongest bridge type there is was dropped
    for two whole sources, and their silence read like the tools disagreeing. Read as a spelling of
    `file.hash` in `store._cell`, in one place rather than in each adapter.
  - **An artifact known only by its path was not an artifact.** `yara_scan` emits `file.path` and
    no `file.name`; osquery file events do the same. `file_canon` read only `file.name`, so a YARA
    match could not bridge to the EVTX that executed the same binary. `file.path` is now a column
    and the basename fallback feeding the join key.
  - Also folded in: the DNS exclusion list was duplicated between an inline SQL literal in
    `correlate.py` and `normalize.is_generic_domain` — two copies that would diverge. It is now the
    derived `dns_generic` column, the same pattern already used for users, hosts, files and IPs.
  - **Two sources entered the store without a usable time.** `registry_regfile` stamped every
    record with `now()` — a .reg export carries no timestamp of its own — so persistence entries
    collapsed onto the moment of analysis: untrue, and unstable enough that two runs of the same
    file disagreed and re-opening an old case moved its persistence to today. `yara_scan` emitted
    no `@timestamp` at all, so `ts_parsed` was NULL and every match fell out of the timeline, the
    episodes and every temporal recipe. Both now take the honest anchor the artifact itself
    provides: the export's mtime, and the matched file's mtime. Both keep `event.kind: "state"` —
    the time says when the state was *observed*, never when the key was written.
    Deleting the false timestamps instead was considered and rejected: nothing in the reports
    surfaces registry findings (the only `ioc.severity` section is THOR's), so a record with no
    time would have been a record nobody sees. A true time is the fix; a missing one would have
    traded a visible lie for an invisible truth.
    The YARA record also gained `file.name`: it named the artifact only by path, which is the
    other half of the bridge fixed above.
  - Measured, not asserted: `eval/correlation_corpus.json` grows to 13 cases and 28 checks, and
    `tests/test_corpus_discriminates.py` to 10 mutations — one per new case, each verified to turn
    its case red. `run_eval` gained a `max_families` bound, because over-counting families is a
    defect with its own consequence, not the harmless direction of the same error.

- **Batch the EVTX ingest — done (2026-07-24).** Hayabusa is invoked once per file and reloads its
  ~5 000 Sigma rules every time; handing it a directory instead is **27x** faster on the local corpus
  (205 s → 7.5 s for 278 files, `docs/analysis/performance.md`). Implemented with a batch-first
  strategy: `run_batch()` in `hayabusa_runner.py` uses `-d` directory mode when there are 2+ EVTX
  files; if the batch invocation fails, `build_records` falls back to the existing per-file
  `ThreadPoolExecutor` path. Single files take the per-file path directly (no overhead). Name
  collisions (duplicate basenames from different directories, the normal case for `Security.evtx`
  collected from several hosts) are handled in `runner.stage_batch_dir` by prefixing a numeric
  counter, via symlinks into a temporary directory.
  What the *measurement* corrected, once batch and per-file were run against the same corpus with a
  deliberately corrupt file in it: **the error contract was already weaker than this list assumed.**
  Hayabusa skips a file it cannot parse and still exits 0, so the per-file path reported nothing
  either — `errors` came back empty both ways, and the corrupt file's absence was indistinguishable
  from a file with no detections. Batching therefore preserves the contract because there was less
  contract than believed, not because it reports per file.
  **Now closed (2026-07-24).** Hayabusa exits 0 on an unreadable file but names it in a per-run
  `logs/errorlog-<ts>.log` and prints a pointer to it; `hayabusa_runner.failed_files` parses that,
  both `run`/`run_batch` take a `skipped` out-parameter, and `build_records` turns each into an
  `errors` entry ("evtx X: skipped by Hayabusa (unreadable or corrupt)") — mapping the staged name
  back to the caller's own when batching renamed a duplicate. That list already reaches the analyst
  everywhere: the CLI prints it, `report_html` banners it, the GUI shows it, the bundle carries it.
  Only basenames are surfaced (§9). A dropped log is no longer an absence to be inferred from a
  shorter timeline.
- **osquery as an ingest source — done (2026-07-24).** Adapter `adapters/osquery_result.py` maps
  osquery NDJSON result logs (nested `columns{}`, epoch `unixTime`) onto the common schema, filling
  the macOS/Linux endpoint gap. CLI: `engine/run_osquery.py`. GUI: content-sniff routing in
  `/api/analyze` (detects `hostIdentifier`+`unixTime` in JSON/LOG files before the generic log
  fallthrough). Tests: `tests/test_osquery.py` (synthetic NDJSON parsing + malformed input).
  Built from the documented result-log format rather than from a sample, which is the one shortcut
  this entry originally ruled out — osquery is free and local, so a genuine log can be produced on
  the box. The cost showed up immediately in the column map: `columns.category` (the FIM group, e.g.
  "homes") was overwriting the ECS `event.category`, `tty` was mapped to a port, and `name` was read
  as a process name in tables where it names a kernel extension. Fixed and pinned by a test.
  **Still open**: `brew install osquery`, produce a real result log, confirm the remaining fields.
  **Out of scope**: deploying or managing agents and fleets — that would make EventHound an EDR

- **CrowdStrike adapter — done (2026-07-24).** Two formats supported: detection clipboard
  (`Key: Value` blocks) and LogScale/CQL JSON (single JSON, NDJSON, `@rawstring:` wrapper). Field

  the export never arrived, but a detection copied out of the console is a real, checkable sample.
  CLI: `engine/run_crowdstrike.py`. GUI: content-sniff routing for `.txt`/`.log` uploads.
  `build_records()` wired with a `crowdstrike` parameter. Cross-source correlation with EVTX/PCAP
  works automatically via the common schema. *(The documentation half of this strand —
  `cs_falcon_docs` and `docs/crowdstrike/` — was removed on 2026-08-27; see "Closed decisions".
  The adapter is unaffected.)*
  Two things the review corrected. `aip` — the agent's *external* address, i.e. the tenant's NAT
  egress, the same value for every host behind it — was being mapped to `source.ip`, where it would

  parameter accepting `[{"rules": path, "target": path}]` dicts, and a `/api/yara-scan` GUI endpoint

  skip, not a failure.

  reaches `/api/yara-scan`". The endpoint is gone rather than wired. `/api/analyze` already applies
  uploaded `.yar` rules to the files no other adapter claimed, and — unlike the dedicated endpoint,
  which returned raw match records — it puts the matches through the store, the correlation and the
  case. Wiring a second road to a weaker version of the same capability is what "one road in"
  (`ca89c7b`) exists to prevent.
- **The kill chain was driven by one source and a half — closed 2026-08-28, the weaker way.**
  Of the 102 records the simulated incident produces across nine tool families, exactly six carried
  an ATT&CK technique: five from `evtx` and one from `yara`. CrowdStrike, THOR, Okta, the generic
  logs, osquery, the registry and **PCAP** carry none, because `kc_phase` is derived from techniques
  and only the endpoint adapters emit them. So the coverage, the narrative, `host_killchain` and the
  map's lanes described a nine-source incident using six records — and the demo read "Command and
  Control: 1 event, evtx" beside a capture containing a metronomic beacon to the C2.
  **Rejected**: attaching `T1571` / `T1071.004` / `T1041` to the network records as hypotheses. Those
  three signals exist today only inside `engine/run_pcap.py`, the standalone slice CLI that does its
  own `Counter` analysis and never touches DuckDB, and promoting them to records would have filled
  the lanes while making the picture mean less — a non-standard port is a reason to look, not
  evidence of a technique, and "a correlation that links everything measures nothing" applies to
  phases exactly as it does to bridges (§6).
  **Done instead**: `correlate.phase_corroboration` states, per phase, what the tools that carry no
  technique were doing in the same window — co-occurrence in time, the relation `episodes` already
  reports, labelled as such and never rendered as a technique. It states the width of the window,
  because "in the same 4 min window" and "in the same 59 min window" are different claims; it
  applies the same exclusions as the rest of the correlation, after the first implementation
  cheerfully named loopback, a machine account and the declared gateway as corroborating evidence;
  and it marks a beacon "(to validate)", since a destination contacted on a metronome is what C2
  looks like and also what a backup agent looks like. `tests/test_correlation.py` asserts the
  exclusions hold and proves the assertion can fail by re-running the view with the infrastructure
  declaration withheld. Reasoning in
  [`docs/analysis/correlation.md`](analysis/correlation.md).
  Still true, and still stated in `analysis/README.md`: the network ATT&CK signals that file
  describes are produced by `run_pcap` in its own Markdown output only and reach no record.

## Closed decisions worth remembering

- **Wrapped, never reimplemented.** Hayabusa, the Eric Zimmerman tools, Zeek and tshark are sensors;
  the value is the schema above them and the correlation between them.
- **Document third-party rule sets, do not vendor them.** Applied to YARA (license variety) and to
  the osquery configuration packs.
- **Native over containers on macOS.** Docker Desktop there is CPU-only and memory-capped by the
  Docker VM, so the native stack is the recommended runtime on macOS; Docker stays for reproducible
  / non-macOS deployments.
- **No bundled LLM, no vector RAG.** *(2026-09-01)* The on-box LLM (Ollama + a small owned tool-calling
  loop) and the vector RAG (Qdrant + fastembed + cross-encoder rerank) were the two heaviest,
  least-validated subsystems and were removed. ATT&CK is already vendored as `attack_map.json` and the
  rest of the grounding knowledge is a few markdown indexes under `method/`, read directly. The
  interpretation layer is now **external** — the analysis MCP server (`analysis/analysis_mcp_server.py`)
  — so reasoning lives in the agent harness (Pi, Claude Code, …), never in a bundled model; EventHound
  stays deterministic and local.
- **No speculative adapters.** An adapter is written against a real sample, never against a format
  guessed from documentation.
- **No vendor product documentation in the RAG.** *(2026-08-27)* `cs_falcon_docs` and
  `sonicwall_docs` were deleted and `docs/crowdstrike/` and `docs/sonicwall/` removed. A vendor's
  manual dates the moment it is indexed, and both vendors now ship an **official MCP server** that
  answers the same questions against the live product; that work belongs in a separate project, not
  here. What stays is the *artifact* side — the CrowdStrike ingest adapter parses an export the
  analyst already holds, exactly like an EVTX or a PCAP. The knowledge base keeps only what grounds the
  analysis itself: frameworks, regulations and ACN.
  Corollary: a product-syntax question has **no** answer here, and saying so is correct.
- **New products are not a standing backlog item.** Okta shipped as a CLI source because a documented
  schema and a plausible sample existed; Microsoft 365 / Entra, Proofpoint and the rest are *not*
  tracked as to-do. They follow from the decision above, not from an ambition to cover every vendor:
  each waits on a real reason to exist — a specific analysis that needs it and a real sample to build
  against — at which point it is picked up deliberately, not because a list said so. An Okta GUI view
  is the same: CLI-first means a source is complete when its CLI works, and the GUI follows demand.
  (This was removed from the list once, re-added by mistake during a review, and removed again — the
  reasoning lives here so it stays removed.)
